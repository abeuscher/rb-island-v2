# Session 006 — Resolve Phase vs. Dummy Opponent — Log

**Date:** 2026-09-17
**Branch:** session-006
**Type:** feature

## What was built

### Phase 1 — Dummy opponent and volley resolution

- `PlanController.new` seeds a static, already-built layout onto the enemy island (a
  cannon at its frontline cell, a generator mid-island) via a new `seedDummyOpponent`
  helper, since there's no bot yet. The dummy's cannon always targets the cell directly
  across the channel from it (`mirrorCell`, reflecting through the board's width — the
  board is symmetric, so this lines up exactly with the frontline cell opposite it).
- `rules.luau` exports two of its previously-internal pieces, `resolvePlayerVolley` and
  `destroyedCellSet`, rather than the full `resolveRound` batch — see the Open Gate
  decision below. Shot records now also carry `owner` and `origin` so a consumer can
  animate a shot without re-deriving where it came from.
- `PlanController:advanceRound()` now runs both sides' volleys against the same
  pre-resolve structure snapshot (matching `resolveRound`'s own simultaneity), applies
  damage and belief-map reveals, and holds the result in `pendingState` rather than
  applying it immediately. A new `onResolve` listener hook lets the render layer animate
  the volley first; `commitResolve()` (called by the render layer) applies the round and
  restarts the PLAN clock. Board clicks and Ready are ignored while `phase == "resolve"`.

### Phase 2 — `src/client/Render.luau` (new)

- Animates every shot from its firing structure to wherever it actually landed
  (`shot.impactCell` — already the blocking cell for a blocked direct shot, so a ridge
  hit needs no special-casing to visibly stop short).
- Renders the enemy island from the local belief map: revealed structures, revealed
  rubble, and a subtle marker over cells never yet scouted; terrain itself was already
  fully rendered for both territories by the existing `Board.luau` (§11: terrain is
  always public).
- Fog now clears progressively as a direct-fire shell crosses each beam-path cell,
  rather than all at once after the round commits (added mid-session per user request).
  Every shot's full reveal footprint (impact, plus splash neighbors for a mortar) fills
  in the instant it lands rather than waiting for commit either. This needed no change
  to the pure fog/rules layer — `fog.luau` still computes the final belief map in one
  deterministic step; only the client's animation reveals it progressively, using timing
  it already derives from the shot's own flight.
- Destroyed structures get a transient rubble marker for the duration of the resolve
  animation; on the enemy side, rubble also persists afterward via the belief map (a
  stale plot, per §11). On the player's own side there's no persistent rubble entry in
  the state model, so it's transient-only — the cell just returns to empty land.

### Phase 3 — Fixes from live testing

- A targeted weapon that was out of range or unaffordable used to fail with zero
  feedback — added a status-bar message naming the reason. Initially this got
  overwritten almost instantly by the next "round begins" message; fixed by holding
  misfire messages on the controller and having `commitResolve` show them instead of
  the generic round message when there are any.
- Targeting a cell out of a weapon's range is now rejected at assignment time
  (`handleBoardClick`'s target branch checks `Flight.range` before accepting a click),
  rather than only failing silently at resolve. `armTarget` now takes the full weapon
  record (not just its key) so this check has the weapon's position and type to work
  with; updated `BuildPalette.luau`'s one call site to match.
- `PLAN_SECONDS` dropped to 10 (from 45) and both weapons' ranges doubled (cannon
  10→20, mortar 16→32), both purely for faster iteration during testing — flagged in
  `config.luau` comments as due for reconsideration once the loop is playtested (§18).
  `flight.spec.luau`'s range assertions were changed to read expectations from
  `config.STRUCTURES.*.range` instead of hardcoded numbers, so tuning passes like this
  don't break tests going forward.

## Scope decisions made along the way

- **Open Gate decision:** wired in `rules.luau`'s `resolvePlayerVolley`/`destroyedCellSet`
  directly rather than the full `resolveRound` batch. `PlanController` applies PLAN-phase
  commands immediately as the player clicks, not batched the way `resolveRound` expects
  both sides' commands — reworking that into the batch model is real cross-cutting scope
  that belongs to **Full match loop and wrapper screens**, once B is a real second player
  instead of a static dummy.
- The dummy's shot is deliberately non-adaptive (fixed cell, fixed target, every round)
  — there's no bot AI yet; that's its own later plan entry. This was surfaced mid-session
  as a point of user confusion (it looked like "shots aren't tied to placement") before
  being confirmed as expected.
- No score/points bookkeeping (`destructionPoints`, `structuresLost`) wired in this
  session — the success criterion is about the volley/damage/reveal loop, not scoring,
  and that's the Result screen's job in **Full match loop and wrapper screens**.

## Verification

`rojo build` ran clean after every phase. `lune run test` stayed green throughout
(71/71) except for one expected break: doubling the weapon ranges broke three
`flight.spec.luau` assertions that hardcoded the old range numbers — fixed by deriving
those expectations from `config.STRUCTURES.*.range` instead (see above), back to 71/71.
New/changed client files were smoke-tested by running them directly under `lune run`,
confirming each fails only on the expected missing Roblox globals (`game`), not a parse
error — same convention as prior sessions.

The user tested live in Studio across this session and drove three real fixes: the
misfire-feedback gap, the range-validation gap, and the progressive fog-reveal request.
All three were verified against the user's actual reported symptoms (e.g., the exact
coordinates of a real out-of-range shot) rather than guessed at blind.

- `PLAN_SECONDS` (10) and both weapons' ranges (cannon 20, mortar 32) are testing-only
  values, not balance-considered — revisit once the loop is playtested (§18), likely

- No visual re-confirmation yet of the progressive fog-reveal animation specifically

  Open Gate as something only a human can judge).
- The dummy opponent's layout and targeting are hardcoded placeholders, not a real bot —
  unblocking that is **Bot opponent**'s job, well downstream.
