## Phases

### Phase 1 — Decide the structural fix

`sim/output/shortlist.md` (Session 017's fresh, time-keyed sweep) found the same structural
problem Session 003's original sweep found: standing points reward built structures over
terrain investment strongly enough that one archetype dominates regardless of match length, and
cannon block rate stays near 0% because a fully-informed scripted agent routes around any ridge
it can see. Neither is fixable by the sweep's own config knobs (points weights, costs, rates).
Read the open questions below and settle on an approach before touching any code.

### Phase 2 — Apply the balance pass

Once Phase 1's approach is decided, re-run (or reuse) the sweep shortlist under it and tune
`config.luau` from the result, per the plan entry's success criterion.

### Phase 3 — Resolve-phase polish, README, self-playtest checklist

The plan entry's remaining, less contentious scope: polish resolve-phase feedback (projectile
arcs, impacts, crumbling rubble, terrain rise/fall), write the README (run/sync/asset-name/
config-tuning instructions), and run every self-playtest check from the proposal (win, loss,
blocked shot, cleared shot, stale plot, exploit check, each victory condition, restart).

## Open questions

Settle these at or before the Open Gate — they're the actual re-derivation Session 017 deferred:

- **Standing points vs. terrain investment:** is the fix a `POINTS` reweighting (lower standing
  weight relative to destruction/terrain-adjacent scoring), a new scoring category for terrain
  work itself, or is this an acceptable structural outcome the balance pass should just tune
  around rather than "fix"? The sweep can't answer this — it only tests points-weight and
  cost/rate knobs, not new scoring categories.
- **Cannon block rate near 0%:** this is a property of the scripted sim archetypes being
  fully-informed (they see the whole board, including elevation, so they never route into a
  ridge they can see). Is a low block rate actually a problem for real human play (imperfect
  information, time pressure) even though it shows up in the sim? If the sim is simply not
  representative here, the fix might be "accept it, the sim isn't measuring the right thing for
  this metric" rather than a config or archetype change.
- **How much of Phase 2 depends on Phase 1:** if Phase 1 concludes "no code fix, just pick
  config values that are good enough given the structural reality," Phase 2 is a normal
  sweep-and-tune. If it concludes a scoring or rules change is needed, Phase 2 should probably
  become its own follow-up session rather than being absorbed here — flag that at the Open Gate
  if so, rather than letting this session's scope creep mid-implementation.
