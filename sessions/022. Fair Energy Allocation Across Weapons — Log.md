# Session 022 — Fair Energy Allocation Across Weapons — Log

**Date:** 2026-09-19
**Branch:** main
**Type:** feature

## What was built

### Phase 1 — Allocation strategy

Proposed at the Open Gate as a simple reorder (check the costlier weapon first each tick) —
confirmed, then invalidated by direct measurement before implementation was finalized: sorting
`planShots`' weapons by descending Energy cost and letting each check-and-spend in that order
turned out to change nothing against the real config numbers (measured cannon 9 / mortar 1 in
60s, identical to Session 021's original bug). The reason: cannon's 1-Energy threshold is so
much lower than mortar's 3 that reordering the same-tick check doesn't matter — cannon still
mops up whatever's in the pool before it ever reaches 3.

The working fix is stronger: a cheaper weapon holds fire entirely (doesn't spend at all) while
a costlier one is also eligible to fire this tick, so the pool accumulates uninterrupted toward
the costlier weapon's threshold instead of being nibbled down a fraction at a time. This
generalizes `sim/loadout.luau`'s hold-fire pattern (a declared category table) into a direct
Energy-cost comparison over the real per-tick candidate set. Measured, this flips the result to
mortar 4 / cannon 1 in the same 60s scenario — the mortar gets its full solo-alone output, but
the cannon is now the suppressed one. Surfaced this numeric outcome (a hard swing, not an even
split) to the user before committing to it; confirmed as the intended tradeoff (ship as-is,
recommended over designing a proportional split, which would need real new design and its own
tuning pass).

Scope: real players and the bot both, with no changes needed to `server/Bot.luau` — it has no
firing/Energy logic of its own (only spends Supply to build); actual weapon fire already goes
through this same `planShots` for every player, bot included.

### Phase 2 — Implementation and test coverage

`src/shared/rules.luau`: `planShots` now builds a `fireCandidates` list (off cooldown, targeted
into enemy territory, in range) sorted costliest-first, then only the costliest cost tier among
that tick's candidates is allowed to spend the shared Energy pool at all.

Added a regression test (`tests/rules.spec.luau`) reproducing Session 021's exact measurement —
cannon + mortar, one generator, both auto-firing, real config values (not `fastConfig`'s
cooldown shortcuts, which would distort cannon's cooldown relative to mortar's and mask the
real dynamic) — confirming the mortar is no longer starved to 1 shot in 60s.

### Phase 3 — Two real bugs found live, outside this entry's scope, fixed the same session

Live-testing this session's fix surfaced a confusing match outcome ("Victory / Opponent
incapacitated" with no damage done and healthy-looking stats) that turned out to be two
separate, pre-existing bugs, not a regression from Phase 1-2:

- **Result screen mislabeled which side was incapacitated.** `Rules.checkVictory` computed
  which side(s) actually hit the grace-expired incapacitation condition but discarded that,
  returning only the points-decided `winner` (incapacitation is decided on points, not an
  automatic win for the other side, per Session 014). `Result.luau`'s `conditionText` inferred
  "who was incapacitated" from `winner == owner`, which is backwards exactly when the
  incapacitated side wins on points. Fixed: `checkVictory` now returns `incapacitatedSide`
  separately; `Result.luau` reads that instead.
- **The real cause: `incapableSince` could never actually clear.** `State.withPlayer` merges
  updates with `pairs()`, which can never observe a `nil` value in a plain Lua table literal —
  `{ incapableSince = nil }` simply omits the key, so `rules.luau`'s intended "clear it once
  recovered" call was a silent no-op. A player briefly incapable early on (a normal opening
  squeeze — cannon before generator) stayed flagged forever even after fully recovering, and
  the match would eventually end on a stale "incapacitation" long after their economy was
  healthy — exactly what the user saw (2 live generators, zero damage taken, still ended that
  way). Fixed with a new `State.setIncapableSince` (direct field assignment, which really can
  clear a key) in place of the generic `withPlayer` merge for this one field.

Both fixes came from the user pushing back on an explanation that didn't fit the visible
stats ("I have no buildings destroyed and 2 generators") — the first fix (label) was real but
not the actual cause; the second (stale flag) was.
