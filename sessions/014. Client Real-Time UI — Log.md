### Phase 2 — Event-driven enemy-board reveal (the load-bearing fix)

`Render.luau`'s `onChange` handler called `renderEnemyBoard()` on every tick, repainting the
whole enemy board from the already-updated belief before the shot animation's own progressive
`reveal()` calls got to it — the exact mechanism Session 013 diagnosed. Removed that per-tick
call; belief only ever changes via a reveal, and `onResolve`'s progressive per-cell reveal is
already the only place that needs to touch the enemy board, so a one-time initial draw is
sufficient. No other mechanism was needed.

### Phase 4 — Live bug: couldn't target a weapon right after placing it

User's live test: placing a weapon and trying to aim it immediately did nothing — no delay
"that made sense." Root cause: both controllers' `getWeapons()` filtered out any
`underConstruction` weapon entirely, hiding it from the target list until construction
finished. The rules layer (`Structures.setTarget`) never required completion either. Removed
the filter in `PlanController.luau`/`PracticeController.luau` so a weapon can be armed and
targeted the instant it's placed, and fires automatically the moment it comes online.

### Phase 5 — Design change: incapacitation decided by score, at the user's request

User's live testing kept ending in an automatic incapacitation loss regardless of score —
Session 013's flagged Supply squeeze (`STARTING_SUPPLY` covers exactly one of a cannon or
generator, never both) meant every practice match reached incapacitation with no generator
ever built, leaving no path to a win during testing. At the user's explicit request ("if my
score is higher... I should win"), `Rules.checkVictory`'s incapacitation branch now resolves
through `decideByPoints` — the same tiebreak chain time-limit and mutual base elimination
already use — instead of automatically awarding the match to the non-incapacitated side. Added
a regression test asserting the incapacitated side still wins if its score is high enough;
updated the existing incapacitation test's description to match (its own assertion was
unaffected, since the winning side there also had the higher score). `lune run test`: 84/84.

### Phase 6 — Live bug: retargeting a live weapon didn't take

User's live test: after re-aiming an already-built weapon (2 catapults, 2 generators in play),
the on-board marker and weapon-list target moved to the new cell, but the weapon kept firing
at the original spot. Root cause: the displayed target came from a client-only `self.targets`
cache, set optimistically the moment a cell was clicked — before the retarget command's result
was known. When the command was rejected, the marker still showed the new (rejected) target
forever while the weapon kept firing at whatever was still authoritatively set. Concretely,
`server/MatchService.luau`'s `_handleTarget` still carried the old `weapon.underConstruction`
rejection Phase 4 had just removed client-side, so it was exactly this mismatch that a freshly
re-armed weapon could hit. Fixed by removing `self.targets` entirely — `PlanController.luau`,
`PracticeController.luau`, `BuildPalette.luau`, and `StructureView.luau` all now read the
displayed target straight off `structure.target` (a player's own structures are always fully
visible, never redacted), so the display can't drift from what's actually firing — and by
dropping `MatchService.luau`'s matching gate to match `Structures.setTarget`'s own, already-
permissive check. `lune run test`: 84/84 (unchanged, client + one server gate). `rojo build`
clean. User confirmed fixed live.

### Phase 7 — Roadmap capture

User asked for two things to be captured as future work rather than built now: the ability to
stop/start a weapon's automatic firing, and — the bigger ask — a per-weapon info card (bottom-
right of the screen) shown on selecting a battlefield weapon, surfacing its range/damage/
cooldown/target plus room for upgrade controls later. Added a new plan-file entry, "Weapon
inspection and control panel" (prerequisite: this session's entry; status open, scope pending
design), rather than building it now — the user explicitly flagged it needs its own design
pass first (how a weapon gets selected on the board, how "disabled" reads visually).
