# Session 010 — Real-Time Paradigm Shift — Brief

**Type:** planning
**Shape:** stub-driven
**Branch:** session-010

## Goal

Turn the round-based → real-time architecture decision made mid-Session-009 into actual
`sessions/plan.md` entries: concrete success criteria, sequencing, and prerequisites for
replacing simultaneous-round resolution with per-weapon cooldowns, continuous economy
accrual, timed construction, and a single fixed-length match clock. This session's artifact
is the plan file itself, updated — not any of the work it describes (see the
`session-protocol` skill's "planning" session type). No implementation happens here.

## Why this is happening

The round/PLAN-RESOLVE alternation exists only because simultaneous-volley resolution (§4)
needed a batch boundary — both sides fire at once, neither sees the other's plan first. Once
weapons fire on their own cooldown against a live target, that reason to batch disappears:
nobody's plan is ever visible to leak in the first place. Session 009 built a working bot
under the round model (done, tested, playable) before this came up — that work isn't wasted,
but everything downstream of it changes shape.

## The mechanics decided so far (carry these into the new entries' success criteria)

- **Setup stays untimed.** No change — it already is.
- **Weapons fire on a cooldown** against their assigned target whenever off-cooldown, in
  range, and unblocked. Replaces "one shot per round."
- **Supply/Energy accrue at a rate** (per second) instead of a lump sum at round-end.
  Generators each contribute a steady Energy rate.
- **Building/terrain edits apply immediately** on command — no more batching, since there's
  no simultaneous-reveal reason to hold commands until a boundary.
- **Construction finishes on a timer** (a `readyAt` instead of "completes when both sides
  ready up").
- **A single match clock** (~180 seconds to start, tune later) replaces `MAX_ROUNDS`.
  Victory conditions (base elimination, incapacitation) get checked continuously instead of
  at round boundaries.

## What survives vs. what needs rework

| Survives close to as-is | Needs rework |
|---|---|
| `flight.luau` (per-shot math) | `rules.luau` (`resolveRound` batch → a tick/event function) |
| `fog.luau` (per-shot reveals) | `economy.luau` (lump accrual → rate-based) |
| `board.luau`, `structures.luau` placement/damage | `state.luau` (round counter → elapsed time / `readyAt` timestamps) |
| `view.luau`, `archetypeKit.luau` candidate/target logic | `server/MatchService.luau` (phase state machine → setup + one live tick loop; this also drops the immediate-apply/replay two-track model entirely, since nothing is secret enough to need it once there's no batch) |
| Client `Cursor.luau`, `Render.luau` per-shot rendering primitives | `server/Bot.luau`'s decision cadence (once-per-round → periodic re-evaluate; staleness tracking moves from round-keyed to time-keyed) |
| | `sim/harness.luau` + `sim/archetypes/*` + `sim/sweep.luau` + `sim/metrics.luau` (discrete rounds → discrete time-steps; every round-keyed metric needs a time-keyed equivalent) |
| | `RoundClock.luau`, `BuildPalette.luau` phase gating, most of `rules.spec.luau`/`state.spec.luau`/`economy.spec.luau` |

The sim harness is the single biggest cost — it's what let 5,000 matches run instantly in a
terminal precisely because rounds were free and discrete.

## Recommended sequencing (turn each into a plan.md entry — adjust as the audit below finds reasons to)

1. **Real-time rules core** — tick-based combat (cooldowns), rate-based economy, timed
   construction. Pure `src/shared/`, fully covered by a rewritten test suite. Everything
   else depends on this.
2. **MatchService real-time loop** — untimed setup → one live phase with a match clock →
   result; commands apply immediately and permanently.
3. **Bot re-adaptation** — periodic re-decide cadence instead of once-per-round; verify
   `Bot:decide`'s natural idempotency (it already only adds what it doesn't have) holds up
   being called repeatedly rather than once.
4. **Client real-time UI** — single match clock, per-weapon cooldown indicators, continuous
   economy display, event-driven shot animation instead of per-round batch animation.
5. **Sim harness rewrite** — discrete-time-step simulation, every metric re-derived.

(4) and (5) can likely run in either order once (1) lands; (3) needs (1) and (2) first.

## One open call worth deciding in this session, not deferring further

**Server tick model:** a fixed heartbeat tick (e.g. evaluate every 0.25–1s) vs. independent
per-weapon timers. Leaning toward a fixed tick — simpler to keep deterministic and
server-authoritative, and gives the sim-harness rewrite something concrete to mirror. Decide
this explicitly in this session since entry 1's success criterion depends on it.
