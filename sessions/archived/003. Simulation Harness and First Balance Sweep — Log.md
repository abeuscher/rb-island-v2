# Session 003 — Simulation Harness and First Balance Sweep — Log

**Date:** 2026-09-17
**Branch:** main
**Type:** feature

## What was built

### Phase 1 — Belief-only view and shared archetype toolkit (`sim/view.luau`, `sim/archetypeKit.luau`)

- `View.new(state, owner)` builds a restricted table carrying only `round`, `board`
  (terrain is public, §11), `owner`, `opponent`, and the owner's own
  `resources`/`structures`/`belief`. Every archetype and helper takes a `View`, never raw
  `MatchState` — there is no field on it that reaches the opponent's real structures, which
  is how §15's hard "belief-only" requirement is enforced rather than merely followed by
  convention.
- `archetypeKit.luau`: candidate-cell search scoped to the owner's own territory columns,
  frontline/backline ordering by distance to the channel, greedy farthest-point spread
  placement, belief-map queries, and a shared `chooseTargets` that assigns every live weapon
  (plus any placed this same round, via `pendingWeaponsFrom`) a legal, unblocked target —
  plotted base first, then plotted generator, then the farthest reachable unexplored cell,
  then any reachable known cell as a last resort.

### Phase 2 — Five scripted archetypes (`sim/archetypes/`)

`highground`, `defilade`, `boomer`, `mortarline`, `sprawl`, matching §15's table. Each
builds `config.NUM_BASES` (3) spread bases in round 1, then follows its own deterministic
build-order policy (only placement spots and target ties are randomized per-seed); all five
share the same targeting policy from `archetypeKit`.

### Phase 3 — Harness (`sim/harness.luau`)

`Harness.runMatch` drives one match to completion entirely through
`Rules.resolveRound`, logging score-by-round, every "place" command issued, every shot
fired (with weapon type and blocked/unblocked, reconstructed from pre-round structures plus
this round's own placements since `rules.luau`'s events don't carry weapon type), and the
round each side first found a real enemy base. `Harness.runRoundRobin` runs every ordered
pair (including self-play) × `matchesPerPair`, reusing the same seed set across every
pairing per §15.

### Phase 4 — Metrics and reporting (`sim/metrics.luau`, `sim/report.luau`)

All of §15's metrics: win-rate matrix, field win rate, rounds-to-first-base distribution
and average fraction, match-length distribution, comeback rate, cannon block rate,
purchase share, victory-condition distribution, and an aggregate (not per-structure-type)
Supply efficiency proxy. `report.luau` writes per-match JSONL, an aggregate CSV, and a
plain-text summary.

### Phase 5 — First parameter sweep (`sim/sweep.luau`, `.lune/sweep.luau`)

Three staged passes, each layering its knobs on the previous pass's best pick rather than
one joint grid: RAISE_COST × CANNON_RANGE × MORTAR_RANGE × ENERGY_PER_GENERATOR, then
SUPPLY_PER_ROUND × RECLAIM_COST, then MAX_ROUNDS × a POINTS-table preset. A config
"survives" if no archetype exceeds 60% against the field, cannon block rate lands between
15–85%, and the round limit doesn't decide almost everything.

### Phase 6 — Entry points (`.lune/sim.luau`, `.lune/sweep.luau`)

`lune run sim` runs the baseline 5,000-match round robin (25 ordered pairs ×
`config.SIM_MATCHES_PER_PAIR`) at the shipped default config and prints the full metrics
report. `lune run sweep` runs the three-pass sweep and writes `sim/output/shortlist.md`.

### Key finding: zero configs survived the sweep

None of the 24 swept points cleared the filter, including at MAX_ROUNDS up to 20 (and a
follow-up probe to 40, outside the swept grid). Two structural causes, confirmed and
written up in `sim/output/shortlist.md`:

1. Standing points (§5.4) reward structures, not terrain — `boomer` (all-economy, no
   terrain spend) takes 85–91% of the field at every swept config, and the win rate
   plateaus rather than climbing further past MAX_ROUNDS=20, so it isn't a match-length
   problem a longer clock would fix.
2. Cannon block rate never exceeds ~2% because terrain is fully public (§11) — every
   archetype checks `Flight.resolveShot` before choosing a target and simply never fires
   into a ridge it can see. RAISE_COST/CANNON_RANGE/MORTAR_RANGE tuning can't reach this;
   it's a targeting-behavior effect, not a numeric one.

Reported as-is rather than manufactured into a nominal shortlist (user's call, mid-session)
— the finding itself is this sweep's real output.

Four `DECISIONS.md` entries: `NUM_BASES`/`SIM_MATCHES_PER_PAIR` additions, the
`CANNON_RANGE`/`MORTAR_RANGE`/POINTS-preset sweep-dimension mapping, and the View-based
enforcement design.

## Deferred / carried forward

- The zero-survivor finding is a real design question for the later **Ship polish and
  balance pass** session: whether standing points should credit terrain investment, and
  whether elevation's role should shift away from "blocks a shot outright" toward something
  a fully-informed agent can't simply route around. Not fixed here — fixing it means either
  changing `rules.luau`'s scoring/combat rules or the archetypes' intelligence, both out of
  this session's scope.
- Supply efficiency is reported only as a match-level aggregate (destruction + standing
  points per Supply spent), not broken down per structure type — `rules.luau`'s event
  stream doesn't carry enough detail (a damage event has no typeId) to attribute a kill to
  the weapon that landed it without extending those events, which is out of scope here.
