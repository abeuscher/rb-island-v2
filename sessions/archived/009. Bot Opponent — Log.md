# Session 009 — Bot Opponent — Log

**Date:** 2026-09-17
**Branch:** session-009
**Type:** feature

## What was built

### Phase 1 — Bot decision-making promoted to shared

- `sim/archetypeKit.luau` (candidate-cell search, spread placement, belief-map queries,
  legal-target selection — all View-only, never raw MatchState) moved to
  `src/shared/archetypeKit.luau`, the same move Session 008 made for `view.luau` when the
  sim's own-fog guarantee became the network's guarantee too. `sim/` isn't part of the Rojo
  tree a real server script syncs from, so the bot couldn't have required it as-is.
  `sim/archetypes/*.luau` and `tests/archetypeKit.spec.luau` now point at the shared copy;
  no behavior changed, only the require path.

### Phase 2 — `server/Bot.luau`

- The §14 FSM: open (bases/generator/cannon), then every round either shapes terrain
  (lowering around bases, raising cannon peaks) or masses cannons/mortars once generators are
  topped up, built on `archetypeKit.luau`'s existing candidate-cell/targeting logic rather
  than written from scratch. Tracks which plotted enemy structures haven't been reconfirmed
  recently and treats old ones as unexplored again for targeting — the "re-probe patience"
  difficulty knob (§14).
- `src/shared/botDifficulty.luau`: the three presets (Shoal/Skirmish/Siege — Supply
  multiplier, re-probe patience, whether elevation is used deliberately), shared so the
  client's picker and the bot read the same three names in the same order.
- The bot is a second seat in `server/MatchService.luau`'s round loop — a virtual owner "B"
  with no real `Player` Instance, evaluated once per PLAN phase the way `sim/harness.luau`
  already drives a scripted archetype, with its commands routed through the exact same
  `_handleSetupCommand`/`_handlePlanCommand`/`_handleTarget` validation a real player's
  commands go through. `PracticeController.luau` is untouched — this is a third, independent
  match-start path, not a replacement for the offline dummy. The Supply multiplier is applied
  directly to the bot's own resources in `MatchService`, before `roundStartState` is
  captured, so the bonus is visible to both the bot's live PLAN-phase preview and the round's
  real `Rules.resolveRound` replay.

### Phase 3 — "Play vs. Bot"

- A third Intro button, starting a match immediately (no matchmaking wait) through the same
  server-authoritative path as "Start Game" — the client's `MatchFound` → `mountOnline` flow
  is unchanged, since from the client's side a bot opponent is indistinguishable from a real
  one.
- The previously-empty `SettingsRegistry.luau` gained its first real entry (a "cycle" row,
  new in `Settings.luau`) for Bot Difficulty.

### Phase 4 — Round-clock fix (found in live playtest)

- The user found the round countdown freezing at 0 from round 2 onward. Cause:
  `server/MatchService.luau` only ever announces the resolve phase over a separate
  `ResolveEvent`, never a `StateUpdate` — so `PlanController.luau`'s `self.phase` never
  actually left `"plan"` client-side, and the "entering a fresh plan phase" transition the
  clock-reset logic watches for never fired past round 1. `PracticeController.luau` already
  handled this correctly (it sets `phase = "resolve"` itself mid-round); `PlanController`
  now does the same in `_onResolveEvent`, which also makes the already-written but previously
  unreachable "Resolving..." label in `RoundClock.luau` show up, and correctly blocks board
  clicks during the resolve animation instead of silently dropping them server-side.

  math, fog reveal, structure placement/damage) survive close to unchanged. Not started this

  guesses, same status as every other tuning constant pending §18's balance pass — except the
  balance pass itself is now downstream of the real-time rearchitecture, not the sim harness
  as currently written.
