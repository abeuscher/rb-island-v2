# Session 008 — Real Two-Player Networking — Brief

**Type:** feature
**Shape:** plan-backed
**Branch:** session-008

## Goal

Two Studio clients matchmake, complete setup, and play a full match against each other
with the server holding all authoritative state — no client ever has an unrevealed enemy
structure in its Instance tree or in a remote payload it receives.

## Plan reference

This session executes the plan file's entry for **Real two-player networking**
(`sessions/plan.md`). Read that entry first — it is canonical for scope, success
criterion, prerequisites, and artifact.

## Session-specific deltas

- Every prior UI session (004-007) has been local-only by explicit precedent — there is no
  `src/server/` code beyond `init.server.luau` disabling character auto-load. This session
  is where that changes for real: §12 (server authority) has to be read and followed in
  full, not deferred again.
- `MatchController`, `PlanController`, and the three wrapper screens (Session 007) all
  currently run entirely client-side against a local `MatchState`, with a scripted dummy
  standing in for the second player (3 bases, a generator, a frontline cannon — seeded via
  `Board.islandBounds`, firing the same fixed shot every round). Deciding what happens to
  that dummy is this session's first real decision — see Open questions.
- `Rules.resolveRound` already returns a fourth `resolution` value (pre-combat state plus
  each side's raw shots/destroyed lists), added in Session 007 specifically so a caller
  other than `PlanController` — e.g. a server-side match loop — could reuse it for
  broadcasting an event stream without re-deriving anything. It's unused by any server code
  yet.
- PLAN-phase commands are currently applied immediately, client-side, via direct
  `State.*` calls (for live board feedback), and only *replayed* through
  `Rules.resolveRound` at round's end. Under real server authority, the client can no
  longer call `State.*` directly at all — every action becomes a `RemoteEvent` *request*
  validated server-side (§12), and the client's own-side preview has to come from
  server-pushed state rather than a local mutation. This is likely the session's biggest
  single piece of rework, bigger than the resolveRound-batch adoption was last session.

## Starting state

- The full match loop (setup → rounds → result) works end to end, entirely client-side,
  against a scripted dummy opponent. No server-held state, no remotes, no matchmaking.
- `Rules.resolveRound(config, state, commandsA, commandsB)` is the pure resolution function
  this session's server loop should call once per round; it already returns everything a
  broadcaster needs (events, victory, and the richer `resolution` data).
- Terrain is already rendered identically for both territories on the client today (public,
  per §11) — that part of the client doesn't need new gating. Structure rendering does:
  `StructureView.luau` currently renders a player's own structures straight from local
  state, and `Render.luau` renders the enemy side from a local belief map that's computed
  client-side. Both need their data to originate from the server instead.
- The housekeeping inbox is empty; nothing to absorb this session.

## Open questions

- **What happens to the dummy opponent.** Replaced outright by a second real Studio client
  for testing, or kept around as a documented single-player practice mode alongside real
  networking? The proposal's bot (§14, **Bot opponent** — the plan entry after this one)
  is the eventual "always have an opponent" answer; this session's own accept criterion
  only requires two real clients to be able to play each other. Worth deciding at the Open
  Gate rather than defaulting either way.
- **How much of `PlanController` survives as-is vs. gets rewritten.** The clean split
  would be: client sends command requests and renders whatever the server pushes back
  (a thin view), server owns the one authoritative `MatchState` and runs `resolveRound`.
  That's a substantial rewrite of `PlanController`, not an extension of it. Worth confirming
  that's the intended shape before it's half-built.
