# Session 016 — New Weapon Types — Brief

**Type:** feature
**Shape:** stub-driven
**Branch:** main

## Goal

Turn "New weapon types: missiles and scout drones" (plan file) from a name-only roadmap item
into working weapons, once their mechanics are actually decided. Nothing about either weapon
is designed yet — this session starts with that design pass, not with code.

## Phases

### Phase 1 — Design (before any code)

Raise these at the Open Gate rather than guessing:

- **Missile:** what does it do that the existing cannon (direct fire) and mortar (arced,
  splash) don't? Candidates: longer range than both at a higher Supply/Energy cost, a slower
  cooldown with bigger single-target damage, or a distinct fire mode entirely. Needs range,
  damage, cooldown, splash (if any), Supply/Energy cost, and unlock timing — the same shape
  every other `config.STRUCTURES` entry has.
- **Scout drone:** is this a weapon at all in the current sense? The existing shape
  (`fire_mode`, `damage`, `Rules.tick`'s automatic-fire gate) assumes something that deals
  damage. A drone that reveals fog without attacking is a different mechanic — possibly a new
  `fire_mode` value (e.g. "scout") that `planShots`/`Fog.applyReveal` handle without damage, or
  possibly not a "weapon" in `config.STRUCTURES` at all. This is a data-shape decision, not a
  detail — worth settling before writing any code.
- Whether the bot (`server/Bot.luau`'s `buildWeapons`) and the sim archetypes need to know
  about either new type in this same session, or whether shipping them player-only first (bot
  ignoring the new roster) is an acceptable first cut.

### Phase 2 — Implement whatever Phase 1 settles on

Config entries (`src/shared/config.luau`), any `Rules.tick`/`Flight.luau`/`Fog.luau` changes
the scout drone's mechanic needs if it isn't plain damage, `BuildPalette.luau` menu entries
(reusing this session's cost/affordability display, not re-deriving it).

### Phase 3 — Bot/sim integration, if Phase 1 scoped it in

`server/Bot.luau`'s `buildWeapons` roster and `Kit.chooseTargets`, if the new types need
bot-side targeting logic beyond what's already generic there.

## Starting state

- Single shot is now the default fire behavior (Session 015); `structure.autoFire` exists as
  the not-yet-exposed flag for continuous fire. Any new weapon type placed through
  `Structures.place` gets this by default like everything else.
- The build palette already shows Supply cost and dims unaffordable tools for the existing
  three "Build ___" buttons — a new weapon type should follow the same pattern, not a new one.
- Live Studio confirmation of Session 015's bot/combat/UI changes is still outstanding — worth
  a quick playtest check before piling more weapon-roster changes on top, if that hasn't
  happened between sessions.

## Out of scope

- The weapon inspection/control panel (separate entry, also design-pending) — don't fold its
  scope in here even though both touch weapon behavior.
- Balance numbers beyond a reasonable placeholder guess — real tuning is "Ship polish and
  balance pass"'s job, same as every other weapon's current numbers.
