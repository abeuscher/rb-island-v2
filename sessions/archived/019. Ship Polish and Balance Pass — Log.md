# Session 019 — Ship Polish and Balance Pass — Log

**Date:** 2026-09-18
**Branch:** main
**Type:** feature

## What was built

### Phase 1 — Deciding the structural fix

The brief's Open Gate proposal (a `POINTS` scoring change to credit terrain investment
directly) was set aside after the user pushed back: real playtesting resolves matches quickly
and decisively, which didn't match the sim's near-100% time-limit share. Investigating that
gap found the real cause — all five scripted archetypes spend a large opening chunk of the
match building generators before ever placing a weapon, and cap themselves at 2-3 weapons
that split fire across whatever's reachable rather than concentrating on one target. Added
`sim/archetypes/rush.luau`: fast opening (cannon before any generator), and a small additive
change to `src/shared/archetypeKit.luau` (`Kit.chooseTargets` gained an optional `focusBases`
parameter) so every weapon commits to the same lowest-coordinate plotted base instead of each
independently randomizing among everything visible. With `rush` in the pool, time-limit share
dropped from ~100% to ~60-70% and terrain investment stopped being uniformly punished
(`highground`, which raises terrain aggressively, became the second-strongest archetype) — no
rules-core scoring change was needed.

### Phase 2 — Balance pass

Re-ran the sweep (`lune run sweep`, both the sweep's own `MATCHES_PER_PAIR` and
`config.SIM_MATCHES_PER_PAIR` halved to 20/100 at the user's request to keep runs from timing
out) with `rush` included. Still zero literal survivors of the sweep's 60%-dominance filter
(best was 66%), which the user explicitly accepted — `rush`'s strength reflects competent
play the other archetypes lack, and rebalancing against it is a defense-side balance pass for
a future session, not this one.

Applying the sweep's own picks live surfaced two of them as actively broken rather than
merely suboptimal, found by building a second archetype (`sim/archetypes/recon.luau`, a
deliberate scout-then-commit strategy at the user's request) and instrumenting shot counts:

- `CANNON_RANGE` 8 (the sweep's pick, down from the old placeholder 20) meant `defilade` —
  which deliberately places cannons behind the frontline — could never reach anything and
  fired zero shots all match. Set to 14: enough for an unelevated frontline cannon to reach
  most of a 12-deep island, full depth once elevated.
- `ENERGY_PER_GENERATOR_PER_SECOND` 0.05 (the sweep's pick, down from the old default 0.1)
  starved mortars (3 Energy/shot) almost entirely, since `Rules.tick`'s `planShots` pays
  cheaper, earlier-built cannons (1 Energy/shot) first every tick and the pool never
  accumulated enough for a mortar's turn. Set to 0.15 — the sweep's other tested candidate,
  not a new guess.
- Added a declared-in-one-place fix to `recon` specifically (not generalized further this
  session, see below): its cannons stand down once a base is found and a mortar exists, so
  Energy banks toward the mortar's harder hit instead of the two weapon types competing for
  the same trickle. `base_elimination` went from ~0.1% to ~5% of matches field-wide after
  this and the energy fix landed.

Final tuned `src/shared/config.luau`: `RAISE_COST` 4→6, `RECLAIM_COST` 12→8,
`SUPPLY_PER_SECOND` 0.5→0.7, `ENERGY_PER_GENERATOR_PER_SECOND` 0.1→0.15 (net, after the
sweep's 0.05 pick was overridden), `MATCH_SECONDS` 180→200, `STRUCTURES.cannon.range` 20→14,
`STRUCTURES.mortar.range` 32→20. `RAISE_COST`/`RECLAIM_COST`/`SUPPLY_PER_SECOND`/
`MATCH_SECONDS` are the sweep's literal picks; the two ranges and the energy rate are manual
overrides of sweep picks that broke on contact with real match data. `tests/rules.spec.luau`
and `tests/tickView.spec.luau` had hardcoded cell distances that assumed the old 20-range
cannon; updated both to fit within 14.

### Phase 3 — Resolve-phase polish and README

Found and fixed a second instance of the "full board rebuild every tick" anti-pattern Session
014 already fixed once for the enemy board: `src/client/UI/init.luau`'s `renderBoard()`
destroyed and rebuilt the player's own terrain from scratch on every `onChange` (i.e. every
~0.5s tick), so a raise/lower/reclaim command never animated — it just popped to the new
height on the next tick. `src/client/Board.luau` gained `ClientBoard.updateCell` (tweens a
single cell's height/position/color) and `UI/init.luau` now diffs the previous board against
the current one, touching only cells that actually changed. Also added a "crumble" tween to
`src/client/Render.luau`'s `spawnRubble` — destroyed structures now settle down from roughly
their built size into the flattened rubble footprint instead of popping directly into it.

Wrote `README.md` (didn't exist before): requirements/tool versions, running tests/sim/sweep
with real match-count figures, syncing into Studio (source → DataModel mapping), and how
config tuning relates to the sweep's survival bar.

### Design discussion — sim weapon roles and loadout matrix

After the balance work, the user asked to step back and discuss the sim's architecture ahead
of adding more weapon types to it. Current state: weapon *stats* are fully centralized
(`config.STRUCTURES`) and already generic in the rules core, but weapon *strategy* is
duplicated inline per archetype file, by literal type name — which is why `missile`/`scout`
(stat-complete since Session 016) are used by the real game and bot but referenced by zero sim
archetypes, and why `defilade`'s unreachable-cannon bug sat undetected all session (`sim/` has
no test coverage at all; only aggregate statistics from multi-minute runs). The user asserted
four things to fold into a redesign: weapons should be incorporated into sim strategy as they're
added, considering their specific strengths; not every archetype needs every weapon — group by
category and run combinations; Energy production should be sized to a loadout's actual draw, or
weapons should stand down when not needed; and base placement should add curated adversarial
layouts alongside the existing random spread, to catch exploration blind spots. Rather than
build this mid-session, it was written up as a new plan-file entry ("Sim weapon roles and
loadout matrix") for a dedicated future session — see `sessions/plan.md`.
