### Phase 2 — PracticeController.luau rewrite

Collapsed phases to `setup → live → result`, dropping `plan`/`resolve` and the whole
`pendingCommands`/`roundStartState`/`advanceRound` batch-replay model. Commands now apply
immediately and permanently via `Rules.applyCommand`, same as `MatchService`. Setup → live
transition uses `State.completeAllConstruction` (session 012's fix, same shape here) and arms
the dummy's frontline cannon with a persistent target once (`Structures.setTarget` persists on
the structure, so no per-round reissue is needed — it fires on its own cooldown from there,
restating the old "fires every round" dummy in tick terms). The tick loop is a local
`RunService.Heartbeat` connection accumulating to `config.TICK_SECONDS`, calling `Rules.tick`
each time it crosses that threshold (a catch-up loop, since there's no real server heartbeat to
piggyback on). `TickView.new` replaces the old hand-rolled resolve-event redaction. `commitResolve`
is now a no-op (state's already committed by the tick that produced it), kept only because
`Render.luau` still calls it post-animation.

### Phase 3 — Live bug: destruction points credited to the wrong side

User's live test showed a match they'd clearly won (dominant recap numbers) end in "Defeat."
Root cause, found in `src/shared/rules.luau`'s `Rules.tick` (pre-existing, from session 011's
real-time rewrite — not something this session's own changes introduced, but surfaced by this
session's first live win/loss test): each player's `destructionPoints` was computed from
`destroyedA`/`destroyedB` in the wrong direction — a player was credited for structures *they*
lost, not structures they destroyed. Invisible on a straight base-elimination finish (score
never enters it), but it flips the outcome whenever a match falls back to score-based deciding.
Fixed by swapping which `destroyed` list feeds which player's `destructionPoints`; added a
regression test ("Rules.tick awards destruction points to the attacker, not to the side that
lost the structure") since nothing in the existing suite exercised an asymmetric kill.

### Phase 4 — Live bug: incapacitation loss mislabeled

A second live test ended in a genuine incapacitation loss (no generator standing, Energy
drained with no income), but the Result screen unconditionally read "Opponent incapacitated"
regardless of which side actually was. Fixed in `src/client/UI/Screens/Result.luau`: replaced
the static `CONDITION_TEXT` lookup with a function that reads `victory.winner` against `owner`
for the incapacitation case ("You were incapacitated" / "Opponent incapacitated" / "Both sides
incapacitated"). Also fixed a second stale entry found in the same table while there:
`round_limit` was renamed `time_limit` back in session 011 and this lookup never picked it up,
so a time-limit finish would have shown the raw condition string.

### Phase 5 — Live bug: fog/projectile reveal no longer progressive

User reported the enemy-island reveal used to trace in as a shot's beam crossed each cell, but
now reveals all at once on impact. First pass: `Render.luau`'s `onChange` handler ran
`effectsFolder:ClearAllChildren()` on every tick (every 0.5s) — shorter than a shot's ~0.9s
flight — which was deleting the in-flight projectile mid-animation. Removed that clear (it was
redundant; `onResolve` already owns clearing `effectsFolder` before a new volley). This did not
fully fix the symptom the user was seeing: `renderEnemyBoard()`, also called every tick via the
same `onChange` handler, redraws the *entire* enemy fog/structure display from the current,
already-fully-updated belief map — so even with the projectile surviving, the full-board redraw
still outraces and overwrites the beam's progressive `reveal()` calls within roughly one tick.
This is the same "board fully rebuilds every tick instead of updating incrementally" limitation
session 012 flagged as cosmetic and deferred to "Client real-time UI" — this session's live
testing shows it's the dominant cause of the instant-reveal symptom, not a minor flicker, and it
affects the real networked/bot match identically (shared `Render.luau`, not Practice-specific).
Left unfixed here — genuinely requires the event-driven rendering "Client real-time UI" already
owns, not a follow-up patch. Plan file updated with this finding (§ below).

### Phase 6 — Balance finding: can't afford an opening cannon and generator together

User's own diagnosis, confirmed against `config.luau`: `STARTING_SUPPLY` (10) covers exactly one
of Cannon (`supply_cost` 10) or Generator (`supply_cost` 8), never both, forcing a player to
sequence them and easily never circle back to the generator — which is why every practice match
tested this session ended in an incapacitation loss (no generator ever built, Energy drains with
no income, no Supply buffer to recover once other spending keeps it under the generator's
threshold). Confirmed as a real, working-as-configured number rather than a logic bug — `config.
luau`'s own comments already flag these as untuned placeholders pending §18, and "Ship polish
and balance pass" is the entry that owns this. Not changed this session; flagged there instead
(§ below) at the user's agreement.
